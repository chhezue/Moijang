# Redirect Loop (로그인 후 다시 /login으로 튕기는 문제)

> `route-group-auth-structure.md`에 흩어져 있던 redirect loop 관련 기록을 하나로 뽑아 정리.
> 발표/면접용으로 쓸 거면 아래 "셀프 체크 4문항"을 먼저 막힘없이 답할 수 있는지 확인할 것 — 안 되면 아직 이 문서를 외운 상태지 이해한 상태가 아님.

## 현상

로그인에 성공했는데도 protected 페이지(`/dashboard/*`)에 도달하지 못하고 다시 `/login`으로 돌아가는 케이스가 있었음. 항상 재현되는 건 아니고 특정 조건에서만 발생 — 처음엔 "확인함"으로 문서에 남겨뒀다가, 나중에 지금 코드(`(root)` route group 통합 이후) 기준으로 다시 열어보니 그 조건으로는 재현이 안 되는 걸 발견 → 재검증 필요.

## 왜 문제로 판단했는가

- **보안 문제 아님** — 인증 자체는 정상 동작. 로그인된 유저가 로그인된 유저로 취급 안 되는 **신뢰성/UX 문제**.
- 유저 입장에서는 "분명히 로그인했는데 또 로그인하라고 한다" — 반복되면 로그인 자체를 포기할 수 있는 이탈 지점.

## 재현 조건을 좁힌 과정

### 1차 시도 — 실패

`page.goto()`로 protected URL에 직접 진입 → 재현 안 됨.

Next.js 소스(`node_modules/next/dist/client/components/router-reducer/prefetch-cache-utils.js`)를 직접 확인: dynamic 세그먼트 기본 staleTime은 설치된 버전(`14.2.35`)에서도 30초 그대로 — 프레임워크가 캐시 정책을 바꾼 게 아니었음.[^staletime]

[^staletime]: **2026-08-10 재검증 필요 표시**: v14.2.35 공식 문서(GitHub `v14.2.35` 태그로 직접 확인)엔 `dynamic` 기본값이 **0초(캐시 안 함)**로 적혀 있어 이 30초와 안 맞음. 이 프로젝트 `next.config.mjs`엔 `staleTimes` 오버라이드가 없어서 설정 차이도 아님. 문서가 말하는 "공개 설정값의 선언된 기본값"과 그때 읽은 "런타임 내부 구현"이 다를 가능성이 있으나 확정 못 함 — 재검증 필요. 단, 이 숫자 불일치가 아래 해결책 선택(대안 비교, 채택 이유)의 타당성을 바꾸진 않음: Server Action + `revalidatePath`는 staleTime이 몇 초든 무효화·이동 순서를 구조적으로 보장하는 방식이라 이 숫자와 무관하게 유효함.

**이유**: Router Cache(`prefetchCache`)는 클라이언트 사이드 **소프트 네비게이션**이 그 URL로 실제 시도됐을 때만 엔트리가 생김. `page.goto()`는 하드 네비게이션이라 JS가 로드되기도 전에 서버가 307을 보내버려서, 애초에 그 URL에 대한 캐시 엔트리 자체가 안 생김.

### 2차 시도 — 성공

```
1. 공개 페이지(hydrate된 상태)에서 protected URL로 가는 <Link> 클릭
   → 소프트 네비, prefetch 캐시 엔트리 생성됨
2. (protected)/layout이 서버에서 redirect() → /login?redirect=X
3. 로그인 성공
4. 순수 router.push(X) → 2번에서 생긴 stale 캐시 엔트리를 재사용
   → 다시 /login으로 튕김 (재현됨, 2/2)
5. 같은 조건에서 Server Action 버전 → 정상 도달 (5/5, 회귀 없음)
```

**정확한 트리거**: "이미 hydrate된 상태에서 소프트 네비게이션으로 그 protected URL 진입을 한 번 시도한 이력이 있어야 함". 콜드 진입(북마크, 주소창 직접 입력, 하드 리프레시)으로는 재현 안 됨.

## 왜 이 해결책을 골랐는가 (대안 비교)

|                    | 기존 (`window.location.href`)                                               | Server Action + `revalidatePath`                                                         | Middleware 도입                                         |
| ------------------ | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 로그인 후 이동     | 하드 리로드 필수                                                            | `redirect()`로 소프트 네비게이션 가능                                                    | 소프트 네비게이션 가능                                  |
| 캐시 무효화 타이밍 | 하드 리로드가 JS 프로세스를 종료시켜 Router Cache 통째로 삭제 → 레이스 없음 | 캐시 무효화와 redirect가 같은 서버 함수 실행 안에서 순차 진행 → 레이스 구조적으로 불가능 | 무관 — 미들웨어는 쿠키만 보고 판단, 만료 토큰 검증 불가 |
| 만료 토큰 처리     | `(protected)/layout`의 `getMyInfoServer()` catch                            | 동일                                                                                     | 여전히 `(protected)/layout` 필요 → 두 곳에서 관리       |
| 채택 여부          | 폐기                                                                        | ✅ 채택                                                                                  | 기각                                                    |

미들웨어를 기각한 이유는 애초에 이 버그와 다른 축이기 때문 — middleware는 "로그인 _전_ 접근 제어" 문제고, redirect loop은 "로그인 _후_ 캐시 무효화" 문제. 게다가 토큰 만료 검증은 middleware가 못 하므로 `(protected)/layout`은 어차피 유지해야 해서, middleware를 얹었을 때 얻는 이득(하드 네비 제거) 대비 복잡도(두 곳에서 인증 로직 관리)가 안 맞음.

## 효과와 그 한계

- **측정값**: 클릭→목적지 도달 시간, 하드 리로드 대비 약 3.6배 개선 (~2653ms → ~730ms)
- **측정 조건**: 각 4~5회 측정한 중앙값(median). 표본이 작아서 통계적으로 엄밀한 신뢰구간은 아님.
- **이 숫자가 말해주지 않는 것**: 캐시 무효화 자체의 속도가 아니라 "하드 리로드 vs 소프트 네비게이션"의 체감 이동 시간 차이. 네트워크 상태, 서버 부하에 따라 달라질 수 있음.
- **회귀 테스트**: `tests/e2e/specs/redirect-loop-link-repro.spec.ts`에 재현 시나리오를 남겨둠. 다만 실행하려면 protected URL로 가는 `<Link>`가 필요해서 임시로 공개 페이지에 심었다가 제거함 — 정식 회귀 테스트로 상시 유지하려면 격리된 테스트 전용 fixture 페이지가 별도로 필요함 (미정). 2026-08-05 재확인: 여전히 fixture가 없어서 이 스펙만 타임아웃 실패 — 즉 이 문서의 "5/5 재현 안 됨"은 자동 회귀가 아니라 그때의 수동 확인 결과에 머물러 있음. `docs/issues/todo.md` 6번에 추적 중.
